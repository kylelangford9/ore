# L1: Card and bake-off

Branch `l1-bakeoff`. Output on D: under `D:\Build Artifacts\ore\bakeoff\`.
L2 runs at the same time on the Rust front end. You own `bakeoff/` and the spike's surface and library additions. L2 owns the move of library names into `data/library.json`. If you add a library verb, add it to the spike's `BUILTINS` and to the card, and list it in your report so the coordinator can carry it into `data/library.json`.

This builder decides two things: whether models write Ore well enough to continue (the stop rule), and which surface they write (P3).

## 1. Spike additions (small, first)
- **Date verbs**, because schedule tasks need them: `days s` (ISO `YYYY-MM-DD` to a day number counted from 1970-01-01; fails on a bad date), `date n` (day number to ISO), `weekday n` (0 = Monday … 6 = Sunday). Add one card line for them. The card must stay ≤ 1,500 tokens on o200k (`spike/tokens.py`).
- **C-style surface variant**, selected by `--surface c` on `ore.py check`/`run`, with its own card `spike/SPEC-CARD-C.txt`:
  - Calls are `f(a, b)` and definitions are `f(a, b) = e` (clauses and guards as before: `f(0) = 1`, `f(n) if n<0 = 0`).
  - The method form `a.f(b, c)` means `f(b, c, a)`: the receiver is the data argument, which goes last. `a.f()` means `f(a)`. A bare `a.k` stays field access.
  - Constructors keep juxtaposition (`Rect 2 3`) or take `Rect(2, 3)`; choose one and write it on the card.
  - Everything else is unchanged: lambdas, `_`, pipes, `match`, `catch`, literals and patterns.
  - Implement it as a parser mode that produces the same AST as surface T, so evaluation is shared.
- After the pilot (section 4), the card is frozen. Changes after that go in the report as recommendations, not into the run.

## 2. Task suite: `bakeoff/tasks/`
120 tasks. 60 are general (`g001`–`g060`, MBPP-like: strings, lists, counting, maps, recursion, parsing, small algorithms). 60 come from Build work (`d001`–`d060`):
- takeoff CSV roll-ups by shape, mark, area or sheet;
- weight per foot parsed from W-shape names (`W12x26` is 26 lb/ft), plate weight (thickness in × width ft × length ft × 40.8 lb);
- pay-app math (scheduled value, previous, this period, retention 10%, dropping to 5% after 50% complete), change-order totals with markup, labor hours × rate, sales tax at a given rate, rounding to cents;
- schedule dates: add N workdays skipping weekends and a list of holidays, workdays between two dates;
- document numbering (`RFI-005`, job numbers like `26.411`), feet-inch strings (`12'-6 1/2"` to inches);
- JSON shaped like MCP tool output (marks with sheet, mark, qty, weight), grouped and summed.

About 10 tasks are whole programs: `main` reads stdin and prints, with grants named in the task.

Each task is `bakeoff/tasks/<id>/task.json`:
```json
{"id":"d014","prompt":"Write tons(csv): ... (plain words, names the function and argument order, says what to return)","entry":"tons",
 "tests":[{"args":["mark,shape,ft,qty\nB1,W8x10,20,4"],"want":{"W8x10":0.4}}],
 "program":null}
```
A program task sets `"program":{"stdin":"...","want_stdout":"...","grants":["io"]}` instead of `tests`.

Value mapping, the same in both languages: a JSON array is a list, a JSON object is a map with string keys, plus numbers, strings and bools. Floats compare with a relative tolerance of 1e-9. Avoid tuples in outputs.

Each task folder also holds `ref.ore` and `ref.py`. Both must pass every test before the task counts; check that with the harness's own checker. Prompts must not hint at either language.

## 3. Harness: `bakeoff/run.py`
- **Models** (P9, with Kyle's note "And codex too"):
  - `claude -p --bare --model claude-sonnet-5-5`, all 120 tasks.
  - `claude -p --bare --model claude-opus-5-5`, a fixed 40-task subset (20 general, 20 domain).
  - `codex exec --skip-git-repo-check --json -o <file> -s read-only`, all 120, run from an empty scratch folder on D:, default model (record which model it reports).
  - Local Gemma `kyle:gemma4-e2b` through Ollama's HTTP API, all 120, concurrency 1. Ports 11434 and 11436 both answer. 11436 is Kyle's live engine, so use 11434 if it is a separate server. If it is the same server, run at concurrency 1 and stop if a request from Kyle's engine shows up as a conflict.
  - Find the exact flags yourself from `claude --help` and `codex exec --help`. Give the model no tools, pass the card as the system prompt, and get JSON output that includes usage.
- **Languages:** `ore` (SPEC-CARD.txt), `python` (system prompt: "Write Python 3.12. Output only code in one fenced block.") and `ore-c` (SPEC-CARD-C.txt). `ore-c` runs only on the 40-task subset, with Sonnet and Codex. The task text is identical across languages.
- **Loop:** generate, extract the code from the fence, then check.
  - Ore: the spike `check`, with the task's tests appended as `test` lines. Program tasks use `run` with the grants and stdin.
  - Python: run in a subprocess with asserts and a 10 s timeout.
  - On a failure, send back the JSON diagnostics or the failing test (left and right values) and ask for a fix. At most 2 fix rounds.
  - Record per attempt: model-reported output tokens, o200k tokens of the extracted code, check pass, tests pass, wall time.
- **Volume:** concurrency ≤ 3 for Claude and Codex. Results append to `D:\Build Artifacts\ore\bakeoff\results\<model>-<lang>.jsonl`, and the harness resumes from them.
  - Before the full run, print the planned number of calls.
  - If Claude or Codex returns a usage-limit or rate-limit error, stop that model, keep what you have, and report it. Never retry-loop against a limit.

## 4. Pilot, then the run
1. Pilot: 10 tasks (5 general, 5 domain) × Sonnet × ore and python. Look at the failures. If the card has a real hole (a verb models expect, an unclear rule), fix the card and the spike once. Then freeze the card: record its sha256 in the report.
2. Full run as above.

## 5. Report: `bakeoff/REPORT.md` (also your final message)
- **G1:** per model, total and median output tokens Ore against Python, on tasks where both final programs pass. Also the o200k counts of the code.
- **G3:** per model and language: first check passes (%), tests pass first try (%), passes within 2 fix rounds (%).
- **P3 rule:** `ore-c` against `ore` on the subset. Switch only if `ore-c` passes first try 5+ points more often, at equal or fewer tokens. State SWITCH or KEEP.
- **Stop rule:** if Ore's first-try pass rate (Sonnet and Codex, the main writers) is more than 10 points below Python's, say STOP in the first line of the report.
- **G7:** card tokens.
- Ore's top 10 failure causes, with the fix you recommend for each (card wording, an alias, a library verb, a better diagnostic).
- Calls made per model, and where the raw results are.

Gate run: the full bake-off itself. Skip unit tests beyond the checker's own self-check on the 120 references.
